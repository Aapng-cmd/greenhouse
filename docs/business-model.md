# Бизнес-модель: вычислительный контур теплицы

## 1. Бизнес-домен

Моделируется **вычислительная система** тепличного хозяйства, а не
гидроконтур как таковой.

Агропредприятие держит теплицу с датчиками температуры, влажности воздуха,
освещённости и вредителей. Каждый съём порождает **заявку на обработку**:
проверить допустимый диапазон, посчитать управляющее воздействие, записать
факт в журнал, при успехе отдать команду актуатору (нагрев, полив, лампа,
химикаты).

Заявка - единица работы **процессора/воркера**, не капля воды и не градус.
Приборы СМО - микросервисы-воркеры (средства ВТ). Физические актуаторы -
эффекторы мира **после** успешного обслуживания. Qt-симулятор - модель
среды и UI, не буфер и не диспетчер.

Источники: И1 температура, И2 влажность, И3 свет, И4 вредители.
На каждый источник - группа из двух воркеров.

## 2. Почему дисциплины варианта уместны в домене

| Дисциплина | Смысл в теплице |
|---|---|
| **ИБ + ИЗ2** | Датчики работают непрерывно; джиттер опроса (сеть, АЦП) близок к равномерному в заданном окне |
| **ПЗ1** | Время расчёта на воркере (валидация + решатель + запись) удобно моделировать экспонентой |
| **Д1ОЗ2** | Журнал входных задач - очередь FIFO со сжатием дыр: новая задача всегда в хвост |
| **Д1ОО4** | При переполнении выбиваем **самую свежую** заявку в очереди (ещё почти не ждала): не теряем уже накопившийся расчёт |
| **Д2Б4** | Свободный воркер группы берёт **одну** заявку самого важного контура (И1 важнее И4). Среди равных - самую старую, потому что новые как раз выбивает Д1ОО4 |
| **Д2П2** | Воркеры внутри группы равноценны; кольцевой указатель не даёт всегда грузить первый прибор группы |

Отказ возможен **только в буфере**. Воркеры не ломаются: они свободны или заняты.

## 3. Роли СМО в бизнес-процессе

```
Съём датчика (источник)
    -> постановка в очередь расчёта (ДП + БП)
    -> при переполнении: выбивание последней поступившей (отказ)
    -> задержка выдачи (BUFFER_DISPATCH)
    -> выбор одной заявки по приоритету источника и воркера группы (ДВ)
    -> расчёт заявки (прибор)
    -> команда актуатору + учёт статистики
```

**Транзакция заявки** - один цикл "показание -> решение -> (команда)".
Для экономического обоснования на этапе эксперимента берётся стоимость
одной такой транзакции (например, амортизация edge-узла + энергия на
расчёт) и сравниваются конфигурации (n источников, m воркеров, ёмкость БП,
интенсивности), пока:

- отказ не выше 10 %;
- загрузка приборов около 90 % (ориентир памятки);
- среднее время заявки в системе минимально среди допустимых.

Итоговая сравнительная таблица заполняется **по прогонам модели**, не
заранее.

## 4. Микросервисы и границы

| Сервис | Бизнес-роль | СМО |
|---|---|---|
| `sensor-*` | Съём показателя | Источник ИБ |
| `dispatcher-put` | Принять задачу в очередь | ДП |
| `buffer` | Очередь расчёта | БП, Д1ОЗ2, Д1ОО4 |
| `dispatcher-select` | Выбрать одну заявку и воркер группы | ДВ, Д2Б4, Д2П2 |
| `worker-*` | Посчитать заявку | Прибор ПЗ1 |
| `event-calendar` | Пошаговый журнал | Календарь особых событий |
| `stats` | KPI контуров | ОР1 |
| `greenhouse-sim` (Qt) | Среда + UI; кадры JSON от `smo.py` | Не буфер |
| `actuator-*` | Исполнить уже посчитанную команду | Эффектор, не прибор |
| Event bus | Контракты между сервисами | Именованные события шины |

Классика: ДП **не** вызывает воркеры. Связь ДП -> приборы отсутствует.

## 5. Триггеры (когда кто работает)

| Событие | Кто | Действие |
|---|---|---|
| Заявка сгенерирована | ДП | `put` в буфер или отказ/выбивание |
| BUFFER_DISPATCH | ДВ | выбрать одну заявку Д2Б4, назначить прибор группы Д2П2 |
| Обслуживание завершено | прибор, stats, актуатор | учёт, команда миру, снова запрос выдачи |

## 6. Общий буфер

Все контуры в одной очереди. Д1ОЗ2 и выбор Д2Б4 читаются прямолинейно
(лучшая заявка = min номер источника, затем min t_gen). Дисциплины
варианта 22 зон не требуют.

## 7. Что сознательно не является СМО

- Датчики не пишут напрямую в Qt: заявка идёт в ДП -> БП -> ДВ -> воркер.
- Тип датчика не балансирует воркеров - это делает ДВ (Д2П2 внутри группы / Д2Б4).
- Нагреватель как "прибор СМО" - это не ВТ-обслуживание заявки.
